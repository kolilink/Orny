# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Orny** is a React Native (Expo) mobile app for managing a small chip factory — SOL Chips in Conakry, Guinea. UI and all labels are in French. Currency is GNF (Guinean Franc). Deployed as a PWA via Netlify (GitHub → auto-deploy).

## Commands

```bash
# Dev server
npx expo start
npx expo start --ios
npx expo start --android
npx expo start --web        # PWA dev mode

# Type-check (no test suite, no linter)
npx tsc --noEmit

# Build web PWA for deploy
npx expo export --platform web   # outputs to dist/

# Push to GitHub triggers Netlify auto-deploy
git push origin main
```

No test suite. No linting config.

## Architecture

### Auth flow
`context/AuthContext.tsx` → `AuthProvider` wraps the app in `App.js`. On startup it calls `supabase.auth.getSession()` with an 8-second outer timeout. `applySession()` loads factory memberships and sets `membershipLoading = true` while running — **AuthGate blocks on both `loading` and `membershipLoading`** to prevent the FactorySetupScreen flash. Memberships are cached in AsyncStorage under `membership_cache_{userId}` so slow networks fall back to cache instead of showing an empty factory list.

Roles: `admin`, `manager`, `investor`, `vendeur`, `inspecteur` — see "Roles" further below (`db/update27.sql`) for the full current permission model, the join/invite flow, and why `manager` (not `employee`) is the name now. Vendeur gets Ventes + Plus (Plus limited to just Clients) — a market-stall seller can sell and manage clients but has no Production/Stock access, no pricing/catalog edit rights, and no visibility into Dépenses/Investisseurs/Rapports/Coach/Fournisseurs. RLS backs this at the DB level (`sales`/`clients` insert+update policies include `vendeur`; every other table's staff policies deliberately don't). There is no Dashboard/Accueil tab for any role — see "Navigation psychology" below.

Email/password + Google OAuth were the only sign-in options; Apple added `signInWithApple()` (native `expo-apple-authentication` → `supabase.auth.signInWithIdToken`) since Apple Guideline 4.8 requires an equivalent option whenever a third-party login like Google is offered on iOS — the `expo-apple-authentication` dependency existed unused in `package.json` (and an unused `appleBtn` style already sat in `LoginScreen.tsx`) before this was actually wired up.

### Store pattern (all stores in `store/`)
Every store follows the same write-through cache pattern:
1. **Read** — hit AsyncStorage immediately (cache key = `${getFactoryId()}_${entity}`)
2. **Write** — write to AsyncStorage first, then sync to Supabase in `.then()`
3. **Sync** — `sync*FromSupabase()` pulls fresh data into the cache

`store/context.ts` holds the active factory UUID in memory. All stores call `getFactoryId()` for their cache namespace. `generateId()` produces UUID v4 for new records.

Full store list: `batches`, `bulks`, `clients`, `context`, `customCategories`, `customerOrders`, `demo`, `documents`, `expenses`, `flavors`, `investmentEntries`, `investorDistributions`, `investors`, `machines`, `production`, `products`, `profile`, `purchases`, `sales`, `stock`, `suppliers`, `weeklyTarget`.

**`store/production.ts` (the original `production_batches` table — potatoes/sachets/gas/hours/yield) is dead for writes.** Since the "Production rebuild" (`update8.sql`) moved actual batch-logging to `store/batches.ts`/`production_batches_v2` (generic product + recipe + `unitsProduced`), nothing calls `store/production.ts`'s `addBatch` anymore — the only `addBatch` call site in the app is `screens/Production/index.tsx`, which imports from `store/batches.ts`. Dashboard used to read the dead table (fixed — now reads `store/batches.ts` + the real per-factory `getWeeklyTarget()` instead of the hardcoded `FACTORY_CONFIG.weeklyProductionTarget`; the "Production cette semaine" card and the "Production en retard" banner were previously stuck at 0 forever for any factory using the current Production screen). **`utils/businessData.ts` (feeds the AI Coach) still reads the dead table and is NOT fixed** — its `sachets80g`/`potatoesUsedKg`/`hoursWorked`/`yieldGramsPerKg` fields have no equivalent in the new generic `Batch` model (which has `unitsProduced` + an arbitrary `materialsUsed` array, not a fixed potato/sachet/gas shape), so Coach's whole production-analysis section (yield, sachets-vs-sales coverage, hours worked) is confidently reporting zeros/stale data for any factory on the current Production screen. Fixing it needs a real redesign of `BusinessSnapshot.production` (and `utils/coachPrompt.ts`, which references those exact field names) around generic units — flagged here rather than fixed, since it changes what Coach's prompt data shape means, not a mechanical import swap like Dashboard's fix was.

**`utils/businessData.ts` was fixed to read the live production tables (2026-07-16).** It previously imported `getBatches` from the dead `store/production.ts` (see above) — `BusinessSnapshot.production` has been redesigned around the generic `Batch` model: `unitsProduced`/`hours` instead of `sachets80g`/`potatoesUsedKg`/`yieldGramsPerKg`, plus a `topProducts` (per-product breakdown) and `materialsConsumedWeek` (grouped by name+unit, since materials are now arbitrary per-recipe and can't be summed across units) field. `utils/coachPrompt.ts`'s `buildDataContext` was updated to match. This also unblocked `utils/runrate.ts` (below), which needs real per-material consumption history to compute anything.

**Stock is now a real finished-goods ledger, not just raw materials.** Every `ProductFlavor` and standalone `BulkProduct` (no `flavorId`) gets its own `stock_items` row (id = the flavor/bulk's own id), auto-created on creation and self-healed (backfilled at 0) for pre-existing ones in `Ventes`' `load()`. A `BulkProduct` that *does* have a `flavorId` has no stock of its own — it's a case of `bagCount` units of that flavor, so selling it deducts `bagCount × qty` from the flavor's own row (`resolveStockTarget()` in `screens/Ventes/index.tsx`). Before this, selling never touched stock at all (finished-goods counts only ever went up, via Production) and buying (`Suppliers > Achats`) never touched stock either — `store/purchases.ts`'s `addPurchase` now increments the linked `stock_item_id`'s level, and the purchase form has a real stock-item picker (with an inline "+ nouvelle matière première" escape hatch) instead of a free-text `product` field that was never connected to anything. `store/stock.ts`'s `checkStockAvailability()` is called before both a sale and a production batch commit — insufficient stock is a confirm-to-override dialog now, not a silent `Math.max(0, ...)` clamp with no warning beyond an easy-to-ignore orange banner.

**Purchases were invisible to the P&L.** `screens/Reports/index.tsx` only ever read `sales` + `expenses` — a raw-material purchase logged in `Suppliers > Achats` never reduced reported profit unless someone *also* re-entered it as an `expenses` row with category `matiere_premiere`. Reports now shows "Achats matières premières" as its own P&L line (`getPurchases()`), with an explicit on-screen warning against double-entering the same cost in both places — there's no automatic de-dupe between the two, that's still on the humans entering data.

**Investor payouts.** `investors`/`investment_entries` only ever tracked capital going *in*. `investor_distributions` (`update10.sql`) tracks capital paid *out* to an investor (profit share, refund, etc.) — admin-only write, investor can read their own. `Investors` screen nets it against `totalForInvestor()` and shows it as a separate red "−" line in the per-investor history, distinct from the green "+" investment entries.

**Business documents are backed up centrally now, not device-local only.** `business_documents.file_uri` used to be a `file://` path — the actual file "stayed on device" (literally the old comment in `store/documents.ts`), so it was unrecoverable on reinstall/loss and invisible to every other member. `update11.sql` adds a private `business-documents` Supabase Storage bucket (RLS keyed on the object path's first segment being the factory id, reusing `my_factory_ids()`/`my_role_in()`) and `business_documents.storage_path`. `addDocument` now uploads via `expo-file-system`'s base64 read + `base64-arraybuffer`'s `decode()` (the same `fetch().blob()`-returns-0-bytes-for-`file://`-URIs workaround documented elsewhere for RN/Hermes) in addition to keeping a same-device local copy for instant preview. `DocumentDetail.tsx` tries the local file first and falls back to a freshly-fetched signed URL (`getSignedDocumentUrl`, 1h expiry) when it's missing — e.g. a different device, or after a reinstall.

**Offline writes now retry instead of vanishing.** Every store's Supabase write used to be pure fire-and-forget — a failure just hit `console.warn` and moved on, with the local cache still showing the write as "saved." Since two of the three real investors using this app check numbers from a different device than whoever made the sale, a write that failed to reach Supabase because the factory floor had no signal was invisible to everyone except the one phone that made it. `lib/syncQueue.ts` is a small persisted (AsyncStorage) FIFO queue: every store's `.then(({error}) => ...)` now calls `enqueueIfNetworkError(error, {...})`, which only queues a *network-shaped* failure (a real RLS/validation rejection is still `console.warn`'d, since retrying that forever would never succeed and would hide an actual bug). `AppNavigator` (`navigation/index.tsx`) drains the queue on mount and on every `AppState` foreground; `<SyncBanner>` (absolute-positioned overlay, since there's no shared `<Screen>`-style wrapper here to thread real layout space through) shows "N modifications en attente de connexion" whenever the queue is non-empty. Not wired into `store/documents.ts` (the file upload itself has different failure semantics — retrying a multi-hundred-KB upload through a small metadata-shaped queue isn't worth it, same reasoning Patron's support-chat images use) or into `weeklyTarget`/`profile`/`customCategories` (low-stakes, not financial/inventory data).

### Navigation (`navigation/index.tsx`)
`AuthGate` renders:
- Spinner while `loading || membershipLoading`
- `LoginScreen` / `RegisterScreen` when no session
- `FactorySetupScreen` when session exists but no membership (new user or pending join)
- `AppNavigator` (Stack + Tab) when fully authenticated

Stack screens (push over tabs) must show a back button — they use `options={{ title: '...', headerTintColor: '#1D9E75' }}` in the navigator. `FactorySettings` and `Profile` manage their own custom back button and keep `headerShown: false`.

### Supabase client (`lib/supabase.ts`)
Uses `expo-secure-store` for session storage on native, falls back to `localStorage` on web (`Platform.OS === 'web'`). `detectSessionInUrl` is `true` on web only (needed for OAuth redirect).

### PWA / web compatibility
- `Alert.alert` with more than 2 buttons does **not** work on web — use a `Modal` with `TouchableOpacity` buttons instead (see approve flow in `screens/FactorySettings/index.tsx`).
- `expo-notifications` is skipped on web (`Platform.OS === 'web'` guard in `utils/notifications.ts`).
- Netlify config: `netlify.toml` sets `NODE_VERSION = "24"` (must match local Node version to keep `package-lock.json` compatible). The `dist/_redirects` rule and `[[redirects]]` in `netlify.toml` handle SPA routing.

### Orny AI (`screens/Coach/`, `supabase/functions/factory-chat/`, `supabase/functions/factory-voice/`)

Rebuilt 2026-07-16 from a client-side, bring-your-own-Anthropic-key chatbot ("Coach IA") into a single-purpose, server-mediated advisor. `utils/businessData.ts` → `getBusinessSnapshot()` still aggregates all stores into a `BusinessSnapshot` client-side (no SECURITY DEFINER RPC layer exists yet for a safe server-side re-fetch, unlike Patron's Alpha) — but the actual model call now goes through `factory-chat`, which holds `GROQ_API_KEY` (`llama-3.3-70b-versatile`) as a Supabase secret and is never reachable without a valid session + real `factory_members` row for the `factory_id` being asked about. The client never talks to Groq directly and never sees the key. `screens/Coach/index.tsx`'s old `API_KEY_STORAGE`/`callClaude`/SecureStore flow is gone entirely.

**System prompt doctrine (`utils/coachPrompt.ts`)** — one singular mission stated explicitly (help this factory make the best product possible, as efficiently as possible, from its own real numbers only), reasoning from three combined frameworks:
- **Musk's 5-step algorithm**, as the mandated order for any concrete problem posed to it: question the requirement → delete the step → simplify what's left → accelerate → automate last, never first.
- **Goldratt's Five Focusing Steps** (Theory of Constraints / *The Goal*): identify the constraint → exploit it fully before investing → subordinate everything else to it → elevate it → repeat, without letting inertia become the next constraint.
- **Toyota Production System**: muda/mura/muri, jidoka, JIT, kaizen, genchi genbutsu.
- Hormozi's revenue-velocity framing (collection rate, ATV, client concentration) carried over from the original prompt.

User-supplied strings (client names, factory name) are sanitised by `s()` in `coachPrompt.ts` to strip prompt-injection characters — unchanged from before.

**Voice mode.** A push-to-talk mic button (native only — `Platform.OS !== 'web'`) records via `expo-audio`, uploads to `factory-voice` (Groq Whisper `whisper-large-v3`, auto-detects language) using FormData's `{ uri, name, type }` object shape rather than `fetch(uri).blob()` — the latter returns a 0-byte blob for `file://` URIs in Hermes, the same gotcha documented for voice/image messages elsewhere in this workspace. The transcript is sent through the same `factory-chat` path as a typed message; the reply is spoken back via on-device `expo-speech` (not a cloud TTS API — free, offline-capable, covers pt/es/en/fr system voices, no added latency/cost/secret). A spoken question always gets a spoken reply regardless of settings; a typed message only auto-speaks if `profiles.voice_autoplay` is on (Profile screen toggle, off by default) — otherwise every AI bubble has a manual 🔊 tap-to-replay. `profiles.preferred_language` is a manual override; absent that, the locale used for TTS is whatever Whisper detected in the most recent voice message (`utils/voice.ts`'s `resolveLocale`). Built for accessibility, not just novelty — French is Orny's default UI language, but the model is instructed to always reply in whichever of French/Portuguese/Spanish/English it was addressed in, both by voice and by typed text.

**`expo-audio`/`expo-speech` are native modules** — added via `npx expo install`, `app.json` gained a configured `expo-audio` plugin entry (`microphonePermission` string, sets both iOS `NSMicrophoneUsageDescription` and Android `RECORD_AUDIO`). Per the OTA-vs-native-build distinction documented elsewhere in this workspace: this needs a real `eas build`, not just a Netlify/OTA-style JS push, before voice mode works on a device that doesn't already have these native modules compiled in.

**Groq key handling.** The live key was shared in a chat session during setup — treat it as exposed and rotate it in the Groq console at the next convenient point, same posture as the Djomi-key incident documented in the sibling Patron app's `CLAUDE.md`. It's stored only as the `GROQ_API_KEY` Supabase Edge Function secret, never in `.env`/`app.json`/any committed file.

### Notifications (`utils/notifications.ts`, `utils/notificationLog.ts`, `supabase/functions/dispatch-notification/`)

Two layers, both new as of 2026-07-16 beyond the original reactive local alerts:
- **Predictive stock alerts** (`checkPredictiveStockAlerts`) — distinct from the original reactive `checkStockAlerts` (fires once `currentLevel <= alertThreshold`). Uses `utils/runrate.ts`'s trailing-14-day consumption rate to warn when an item is projected to hit zero within 5 days, even while still above its threshold. Consumption is computed gross (production draw-down via `materialsUsed`, matched by `rawMaterialId`; finished-goods draw-down via `sales`, matched by product **name** since `Sale` carries no stock item id) — never netted against purchases/restocks, since `currentLevel` already reflects those and subtracting them again would understate the true burn rate.
- **Real push**, not just local `expo-notifications`. `push_tokens` (`update12.sql`, keyed by the Expo push token itself so one device keeps one row across logins) + `dispatch-notification` edge function — resolves recipients server-side from real `factory_members` rows, never trusts a client-supplied user list. Registered once per app open in `navigation/index.tsx`'s `AppNavigator` via `lib/pushToken.ts`, which silently no-ops until `extra.eas.projectId` exists (see "Store submission readiness" above — `eas init` hasn't been run yet).

Every alert (local or push-eligible) is also appended to `utils/notificationLog.ts`, a small on-device AsyncStorage list (last 50, per factory) — previously an alert vanished the moment it was dismissed from the OS tray with no in-app record at all. `screens/Notifications/` renders it.

### Machines (`screens/Machines/`, `store/machines.ts`)

Added 2026-07-16, ahead of real machine data being entered — `machines` (name, type, `rated_capacity`/`capacity_unit`, `status`: running/idle/down/maintenance) + `machine_status_log` (append-only status history, `update14.sql`). Same RLS posture as production/stock: admin/employee write, all members read, vendeur gets nothing extra. Already wired into `utils/businessData.ts`'s `BusinessSnapshot.machines` and `coachPrompt.ts`'s data context (renders "Aucune machine enregistrée" until populated) — the point of building this ahead of real data is that Orny AI can reason about actual-vs-rated capacity (a real Goldratt "exploit the constraint" signal) the moment machines are entered, with no further code changes.

### Design system (`theme/tokens.ts`, `components/ui/`)

Adopted app-wide 2026-07-16 — screens no longer define a local `C` constant per file (superseding the "Color palette" note that used to be here). Palette: `moss` (the one accent, unchanged brand green `#1D9E75`), `paper`/`ink`/`line`/`muted`/`card` for surface/text/border, `caution`/`critical` (a two-step warm severity gradient, replacing a flatter red/orange "alarm" pair — several screens like Créances' debt aging and Stock's level thresholds genuinely need two severity steps, not one). `components/ui/AppModal.tsx` is the one modal/sheet primitive: bottom sheet on phone-width viewports, centered dialog on tablet/desktop PWA widths (`useWindowDimensions`, not `Platform.OS`, since the same PWA build serves both), built on RN's built-in `Animated` (no `react-native-reanimated` dependency, keeping this app's footprint small for low-end Android devices). `ConfirmDialog` (built on `AppModal`) replaces the copy-pasted confirm-overlay pattern previously duplicated per screen. `Toast`/`toast.success()` mirrors Patron's `AppToast` ergonomics (separate implementation).

**RULE — never wrap an `AppModal`'s children in your own `KeyboardAvoidingView`. Keyboard handling lives inside `AppModal` itself, once, for every modal in the app, permanently (fixed 2026-09-05).** Found live on the new Investisseurs screen: "Ajouter un apport"'s Montant field vanished behind the keyboard the instant it opened. Root cause, once traced: every single call site across the app (~15 screens) wrapped its own `AppModal` children in `<KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : undefined}>` — broken on **both** platforms, not just one. On Android, `behavior: undefined` means the component does nothing at all; the keyboard was left entirely to a portalled RN `<Modal>`'s own native window, which does not reliably inherit the main Activity's automatic resize the way a plain in-flow screen does. On iOS, `"padding"` had nowhere to push against: nested inside `AppModal`'s own fixed-`maxHeight` bottom sheet, adding padding just grew the sheet's content without ever moving the sheet itself, so a focused field near the bottom could sit fully behind the keyboard with no way to reveal it — exactly what happened here. `AppModal` now measures the real keyboard height directly via `Keyboard` events (`keyboardWillShow/Hide` on iOS, `keyboardDidShow/Hide` on Android — deliberately bypassing `KeyboardAvoidingView`'s per-platform heuristics rather than trying to tune them) and uses it to (1) shrink the sheet/dialog's own max height so it always fits in the space still visible above the keyboard, and (2) lift the bottom sheet by that same height so it's never covered. A `LayoutAnimation` (opt-in enabled for pre-New-Architecture Android at module scope) keeps the shift smooth and roughly in sync with the keyboard's own animation. Content that needs to scroll still uses a plain `<ScrollView keyboardShouldPersistTaps="handled">` inside — just never a `KeyboardAvoidingView` around it; `AppModal`'s own `body` wrapper (`flexShrink: 1`) is what lets that inner ScrollView resolve a real bounded height and actually scroll instead of overflowing past the sheet's rounded corners once its max height shrinks.

Every pre-existing `KeyboardAvoidingView` directly wrapping an `AppModal`'s children was removed in the same pass (Suppliers ×2 files, Ventes, Clients, Flavors, Bulks, FactorySettings, Production ×3, Investors ×2 files) — each was purely redundant/harmful dead weight once `AppModal` owns this itself. Two more raw, never-migrated `<Modal>`s with their own hand-rolled `KeyboardAvoidingView` and a real `TextInput` were found and converted to `AppModal` in the same sweep, since they carried the identical bug independent of `AppModal` ever being involved: `screens/Stock/index.tsx`'s "Mettre à jour le stock" and "Nouvel article de stock" modals, and `screens/Plus/index.tsx`'s account-deletion confirmation (the one requiring the user to type a confirmation word into a `TextInput` — the most consequential place this bug could have hidden, since a user unable to see what they typed could not complete or safely abandon an irreversible action). A remaining raw `<Modal>` in `screens/Auth/FactorySetupScreen.tsx` (cancel-join-request) was deliberately left alone — it has no `TextInput` at all, so no keyboard ever opens on it and it isn't exposed to this bug class. **Any new modal must be built on `AppModal`, never a raw `<Modal>` plus a hand-rolled `KeyboardAvoidingView` — the moment that pattern reappears, this exact bug reappears with it.**

### Key domain concepts
- **Sales** — `cash`, `orange_money`, `credit`. `amountPaid` tracks partial payments. `isSalePaid` / `saleDebt` helpers live in `types/index.ts`.
- **Production batches** — generic since the "Production rebuild" (`update8.sql`): a `Batch` has `unitsProduced` + an arbitrary `materialsUsed` array (not a fixed potato/sachet/gas shape). The legacy `ProductionBatch` type (potatoes/sachets/gas/hours/yield) only describes the dead `store/production.ts` table.
- **Stock** — a real finished-goods + raw-materials ledger (see "Stock is now a real finished-goods ledger" above), not the original fixed four-input model. Thresholds are per-item (`stock_items.alert_threshold`), not `FACTORY_CONFIG.stockAlerts`.
- **Inventory runrate** (`utils/runrate.ts`) — trailing-14-day daily consumption + projected days-of-cover per stock item, feeding both predictive notifications and Orny AI's data block.
- **Expenses** — 7 categories: `loyer`, `salaire`, `matiere_premiere`, `energie`, `transport`, `maintenance`, `autre`. Drive real P&L in Dashboard and Reports.
- **Customer orders** — pipeline: `pending → ready → delivered / cancelled`. Late-delivery alerts on Dashboard open.
- **Créances** — debt aging grouped by client, color-coded by age, from existing `sales` table (no extra table).
- **Multi-factory** — `allMemberships` + `switchFactory()` in AuthContext. Last-used factory persisted in AsyncStorage key `active_factory_id`.
- **Weekly target** — stored per-factory in AsyncStorage via `store/weeklyTarget.ts`. Editable by admin in `screens/FactorySettings/`.

| `db/update17_security_hardening.sql` | Fix, found live via `supabase db advisors --linked` (not a code read): `lookup_factory_by_code(text)` was directly callable by both `anon` and `authenticated` via `/rest/v1/rpc/lookup_factory_by_code` — confirmed with a raw curl call, not just the advisor's say-so. The app never calls this RPC directly; only the `lookup-factory` edge function does (over its own service-role client), after enforcing a 5-attempts/60s per-IP throttle via `invite_lookup_log`. Calling the RPC straight from a client with only the public anon key skipped that edge function — and its rate limit — entirely, so every 8-character invite code was brute-forceable with zero throttling. Fixed with `REVOKE EXECUTE ... ### Reconciliation (`db/update18_reconciliation.sql`, FactorySettings → "Vérification des données")

"If something is wrong, we will know" — a fixed set of SQL checks, run on demand by an admin, that re-derive facts from the raw tables and flag anywhere they disagree with a stored/computed value. Deliberately scoped to what this schema can actually support, not a port of Patron's 78-check system: Orny has **no append-only stock-movement ledger** (unlike Patron's `stock_moves`) — `stock_items.current_level` is a running total with no history to replay it against — so "does stock match its own movement history" isn't buildable yet; that needs a real ledger (every sale/purchase/production-batch write site instrumented), which is separate scope, not something to fake inside a reconciliation pass. What the current checks cover: row-level arithmetic (`sales`/`purchases`/`customer_orders` totals vs `quantity × unit_price`, overpayment, negative/invalid values), `stock_items.current_level < 0`, invalid expense amounts, and investor distributions exceeding investor contributions (the one aggregate-vs-aggregate check, mirroring Patron's check #77 for capital injections/withdrawals).

**A first version had a 7th check — `investors.amount_invested` vs `sum(investment_entries.amount)` — that looked like the same "cached snapshot vs. ledger" shape as every other check here, and wasn't.** `screens/Investors/index.tsx`'s `handleSaveInvestor()` deliberately writes a new investor's typed "initial amount" into a real `investment_entries` row, then zeroes `amount_invested` right back to 0 in the same flow — 0-vs-a-real-entries-sum is the correct, intended terminal state for every investor created this way, not drift. Caught by actually running the function against production before calling it done: the very first real run flagged a genuine investor (0 vs 4,653,000 GNF in entries) as a false positive. Removed rather than patched — `amount_invested` has no invariant left to check once you know its real lifecycle, it's a legacy field whose value only matters for rows that predate `investment_entries`. **Lesson for any future check here: two fields that look like "cache vs. source of truth" only actually are one if you've traced the write path that's supposed to keep them in sync — read the code that writes both sides before assuming disagreement means corruption.**

**The guard itself was also wrong on the first pass, and this one was a real, live security bug, not a false positive.** `run_factory_reconciliation` is `SECURITY DEFINER`, so its own `RETURN QUERY` reads `reconciliation_findings` with RLS bypassed internally — the admin check inside the function body is the *only* real gate, the table's RLS policy doesn't help here. The first version wrote it as `if my_role_in(p_factory_id) <> 'admin' then raise exception`, exactly the NULL-bypass shape documented at length in the sibling Patron app's `CLAUDE.md`: for a caller who isn't a member of `p_factory_id` at all, `my_role_in()` returns NULL, `NULL <> 'admin'` is NULL, and `if NULL then raise` is silently skipped in PL/pgSQL — so any authenticated user, member of any factory or none, could pass an arbitrary `p_factory_id` and get back that factory's real sales/investor figures in the returned `message` text, plus wipe its `reconciliation_findings` history as a side effect of the `DELETE` that runs before the checks. Caught before ever being reachable from the app (raw SQL testing via `supabase db query --linked` naturally runs with `auth.uid()` NULL, which is exactly the condition that triggers the bug) and fixed with the safe `if not exists (select 1 from factory_members where factory_id = p_factory_id and user_id = auth.uid() and role = 'admin')` pattern — verified live post-fix, both that a non-admin call now raises and that a real admin call still returns findings. **Any new SECURITY DEFINER function with an internal role guard must use `NOT EXISTS (...)`, never `my_role_in(...) <> 'x'` or `= 'x'` in a PL/pgSQL `IF` — that comparison-based form is only safe inside an RLS `USING`/`WITH CHECK` clause, where Postgres treats a NULL result as deny; the exact same expression inside a plain `IF` statement treats NULL as "don't raise," which is the opposite of safe.**

No cron/email delivery yet (Orny has none of Patron's `pg_cron`/Resend infrastructure) — this is on-demand only, triggered by an admin tapping "Vérifier" in FactorySettings. A scheduled version (daily, pushed via `dispatch-notification` to admins when findings exist) is a natural next step once this on-demand version has proven itself against real data for a while, not built preemptively.

### Investisseurs (`screens/Investors/`, redesigned 2026-09-05, superseding the same-day App-wide-pass bullet above)

The App-wide pass's first fix (flatten the per-investor 3-stat grid, "•••" overflow for history entries) kept the original single-screen shape: every investor rendered as an expandable card containing an always-visible stat grid plus a collapsible "Historique (N mouvements)" accordion. Direct follow-up feedback called that shape itself the problem, not just its per-row styling — too much information competing on one screen, no obvious click-through, and no single number answering "how much of the business is actually theirs." Rebuilt onto the exact `Suppliers` → `SupplierDetail` split (same architecture, second time this app has needed it): `screens/Investors/index.tsx` is now a plain list (avatar, name, one subtitle — total + % of capital — chevron, nothing else), and a new `screens/Investors/InvestorDetail.tsx` (`RootStackParamList.InvestorDetail: { investorId }`, registered in `navigation/index.tsx`) holds everything about one investor's account.

**The three facts requested explicitly — how much, when, and their share of the total — are the hero, not something computed by reading a stat grid.** `InvestorDetail`'s hero shows "Total investi" and "Part du capital" as the two headline numbers; the latter is **computed** (`total / grandTotal`, `grandTotal` summed across every investor's `amountInvested + entries − distributions`, fetched alongside this one investor's own data) rather than the pre-existing manual `sharePercentage` field — matching "the investors know... the percentage they have in total, they don't have to calculate that" literally. The manual `sharePercentage` field wasn't deleted (a real business might still want a formally-agreed equity split, distinct from a capital-weighted share, and the list screen's top `summaryCard` — Capital total / Parts distribuées / Fondateur — already depends on it existing) — it's demoted to a small conditional caption ("Part fixée : X%", hidden entirely at 0) and only editable via the investor-level "•••" → Modifier sheet, never shown as a primary stat.

**History is a flat, unranked, newest-first list — deliberately not month-grouped the way Suppliers' purchase history is.** Suppliers' `MonthGroup` collapsing exists because a supplier can generate many purchases a month; one investor's apports/retraits are inherently rare (the whole old screen's complaint was that a handful of movements didn't need an accordion to hide them), so grouping/collapsing here would be solving a density problem this screen doesn't have. Each movement row shows amount (sign-prefixed, `+`/`−`) and date directly — "when that was" is answered by every row, not by opening anything.

**Only a withdrawal's amount takes a distinct color (`palette.caution`, not `palette.critical`)** — a deliberate, narrower call than "no red," consistent with the session's running principle that color should mark a real signal, not be applied routinely: reducing an investor's capital is a genuinely different kind of event from an inbound apport, worth distinguishing at a glance, but it's a normal, expected business action (not a debt/danger/destructive state), so it gets the app's amber caution token rather than its red critical one.

**Primary/secondary action asymmetry mirrors the literal ask** ("I can add money for them" was explicit; withdrawal was never mentioned): a full-width pinned "Ajouter un apport" button is the one prominent action on the screen; "Retirer des fonds" is a small plain-text link beneath it, and its own modal keeps the app's `danger`-variant confirm button since a withdrawal still reduces recorded capital.

**Everything from the old single-screen version that had real logic behind it was relocated, not dropped**: the 3-edits/24h AsyncStorage rate limit on entry edits (`checkEditAllowed`/`recordEdit`, unchanged), the DB-trigger-backed edit-history viewer (`getEntryEditHistory`, before/after diff rendering), and the investor-level edit/delete (delete cascades to that investor's entries, matching the old `confirmDeleteInvestor` behavior) all now live on `InvestorDetail` behind the same "•••" overflow pattern `SupplierDetail` established — one per-movement menu (Historique/Modifier only for entries — a legacy `amountInvested` "base" row and any distribution can only be deleted, never edited/history'd) and one header-level menu for the investor record itself.

**The list screen's top-level `summaryCard` (Capital total / Parts distribuées / Fondateur) was left exactly as it was** — it's a single aggregate glance, not per-row clutter, and the original complaint was specifically about each investor's own card being overloaded, not about this one already-minimal summary.

### Navigation psychology — "sell, sell, sell" (2026-09-05)

Direct product request, not a code-quality pass: the founder looked at the app's own Accueil (Dashboard) tab — a KPI grid, a 7-day sales chart, a production-progress bar, all in front of the seller the instant the app opens — and asked for it gone, on explicit psychological grounds: a seller-facing role opening the app to a wall of numbers gets invited to *look at* the business instead of *run* it, and every screen/step/field that isn't the sale itself is time a real customer stands there waiting. Two changes came out of this, both rooted in the same principle applied in opposite directions.

**`screens/Dashboard/` is deleted outright, not hidden or repurposed** — every KPI it showed had (or now has) a real home elsewhere, so keeping a stripped Dashboard around as an empty landing screen would just be a dead tab:
- Revenue/margin/client-count were already duplicated on Reports (Bilan).
- **Trésorerie (cash on hand) had no other home and would have been silently lost** — added to `screens/Reports/index.tsx` as an always-visible stat (unlike the conditional credit/supplier-debt row below it, a live balance isn't a settle-to-zero risk), computed via the same `computeCashOnHand()` and gated the same way (`role !== 'inspecteur'`, since that role has no read access to capital-injection/distribution rows per `db/update15.sql`).
- **"Production cette semaine" (the weekly-target progress bar) moved onto `screens/Production/index.tsx` itself**, not Reports — a production worker is looking at that screen when they're about to log a batch, which is the one moment this number is actually actionable; a finance report is the wrong home for it. The "Production en retard sur l'objectif" banner moved with it, using the identical threshold (`dayOfWeek >= 3 && weeklyUnits < target * 0.5`) — unchanged logic, just relocated.
- **`checkStockAlerts`/`checkOverdueOrders`/`checkPredictiveStockAlerts` (real push notifications, not just visual banners) were, until this pass, only ever triggered from Dashboard's own `load()`** — deleting the tab outright would have silently killed every one of these alerts with no error, no crash, nothing to notice until a merchant asked "why didn't I get warned about this." Fixed by adding `runAlertChecks()` (`utils/notifications.ts`) — a single entry point that fetches stock/batches/sales/orders itself and runs all three checks — called from the app-level `AppState` foreground listener in `navigation/index.tsx`, alongside the existing `drainSyncQueue()`. This is the one loud lesson from this pass: **before deleting a screen, grep for every side effect it was the only caller of** — a screen can be load-bearing for something that has nothing to do with what it renders.
- `isLosingMoney` (the old "vous perdez de l'argent" banner) has no replacement notification — it's exactly the kind of passive financial-health signal this pass is trying to keep out of the seller's way, and it's already covered by Reports' own profit hero (colored red when negative) for whoever actually opens that screen.

**Tab bar changes, applied per role, not uniformly** — the psychology cuts both ways depending on what a role is actually for:
- `FullTabNavigator` (admin/employee) and `VendeurTabNavigator` (vendeur): no Accueil tab at all — **Ventes is now the first tab**, so it's what a seller-facing role lands on the instant the app opens, replacing a numbers screen with the one screen whose entire job is selling.
- `RestrictedTabNavigator` (investor/inspecteur): the opposite call, deliberately — these two roles can't sell at all and exist specifically to look at the numbers, so their first tab is now **Reports (Bilan) directly**, not a stripped Dashboard and not a bare Plus menu requiring an extra tap to reach the one thing they're here for. ### Production — reusable formulas (`screens/Production/index.tsx`, `db/update21.sql`, 2026-09-05)

Direct request, framed explicitly around Goldratt/Elon-style "simplify, then automate": logging a batch used to mean re-typing every raw-material quantity by hand, every single time, because the old `Product.lastRecipe` only ever remembered the *absolute* amounts from the most recent batch — producing a batch twice the size of last time meant manually doubling every ingredient yourself. `recipePerUnit` (replacing `lastRecipe`, see `db/update21.sql`'s own note above for why it's a new field, not a rename) is a true per-unit ratio, so the app now does that arithmetic instead of the person on the floor.

**Zero separate "set up your formula" step — the first real batch defines it.** `doSave()` only writes `recipePerUnit` when a product's is still empty (`length === 0`), deriving it as `quantity ÷ unitsProduced` for whatever was actually typed on that first batch. Every batch after that reads the formula, never (re)writes it — a one-off adjustment during real production (running short on an ingredient, a rounding correction) must never silently corrupt the master ratio going forward. Deliberately changing the formula goes through a new, explicit "Modifier la formule" action instead (the same "•••" product-actions overflow that already had Renommer/Voir l'historique/Supprimer), reusing the exact same material-row-editing UI as the batch log — no second, parallel form was built for it.

**Auto-scale is a `useEffect` keyed on "Combien ?", not on typing into the material rows themselves.** Every time the produced-quantity field changes, each material row that's actually part of the stored formula (matched by `rawMaterialId`) recomputes to `formulaQty × units`, rounded to 2 decimals; a material added ad hoc for just this one batch (via "Ajouter une matière," not present in `recipePerUnit`) is left alone, since it has no ratio to scale from and was never meant to join the formula automatically. This is also why `selectProduct()` now seeds every formula-backed material row with a *blank* quantity instead of the formula's raw per-unit number — showing "0.5" before anyone has typed a batch size would read as a real (and wrong) default.

**A real gap surfaced while building this, flagged the same day and fixed immediately after (see "Production — produces directly into Saveurs/Lots" below): Production's `Product` entities (`production_products`) and Ventes' `ProductFlavor`/`BulkProduct` entities (`flavors`/`bulks`) were two completely independent catalogs with no linking id anywhere in the code** — `recordStockAddition(selectedProduct!.id, ...)` in Production credited stock to the *production* product's own id, while Ventes' whole sell flow read and deducted stock keyed by the *flavor's* id. Producing a batch incremented a stock pool Ventes could never sell against; the flavor's own sellable stock never moved. Confirmed with the founder before fixing rather than guessed at — this section's own `selectedProduct`/`Product`/"Nouveau produit" references below describe the *original*, now-superseded version of this screen; the current implementation is described in the follow-up section.

### Security audit (2026-09-05)

Ran a full pass over RLS policies, every SECURITY DEFINER RPC, all four edge functions (`lookup-factory`, `dispatch-notification`, `factory-chat`, `factory-voice`), and `AuthContext.tsx`, using `supabase db advisors --linked` against the live project (ref `mtjyeexwvwrhwjzmttmc`) as ground truth rather than trusting a source-code read alone — the one real finding (`lookup_factory_by_code`'s rate-limit bypass) is now `update17_security_hardening.sql` above, applied to production and verified live (edge function still returns `{"factory":null}` for a bad code; the direct RPC now returns `42501 permission denied`).

Confirmed **not** vulnerable to Patron's own historical NULL-bypass bug class (documented in the sibling app's `CLAUDE.md`): every RLS policy here uses `my_role_in(factory_id) = 'admin'` / `IN (...)` predicates, and Postgres RLS treats a NULL predicate result as deny — unlike a PL/pgSQL `IF NOT (role = ...) THEN RAISE` guard, where a NULL condition silently evaluates to false and skips the check. `my_role_in()` returns NULL for a non-member by construction, so a non-member/wrong-role caller is denied by every single policy in the schema, not just the ones someone remembered to double-guard. `approve_join_request()` (the one write RPC with its own hand-written PL/pgSQL guard, not just RLS) uses an explicit `if not exists (select 1 from factory_members where ...)` — correctly fails closed regardless of NULL, not the vulnerable pattern.

Client-side omissions that looked like gaps on first read but are safe because RLS is the real gate (same "frontend is defense-in-depth" posture as Patron): `AuthContext.tsx`'s `updateMemberRole`/`removeMember` never check the caller is admin, and `rejectJoinRequest` never filters by `factory_id` — all three rely entirely on `factory_members`'/`join_requests`' own admin-only UPDATE/DELETE policies, verified present and correctly scoped in `master.sql`.

### OTA updates — a version bump on one platform can silently break the other platform's update (found live, 2026-09-12)

`eas update` failed silently in a way that would have been easy to miss without checking: publishing to the Android platform produced a runtime version that did **not** match what was actually embedded in the Android binary just built moments earlier via `eas build --platform all --profile production` — meaning that Android build would never have received the update at all (a runtime-version mismatch fails silently: no error, the device just never sees an update available). The iOS publish, from the exact same `eas update --platform all` invocation, matched its own build correctly.

**Root cause, confirmed with `eas fingerprint:compare --build-id <id>` (not guessed) — `@expo/fingerprint`'s "fingerprint" runtime-version policy hashes the *entire* Expo app config, not just the fields relevant to the platform being fingerprinted.** `eas build --platform all` with `autoIncrement: true` bumps **both** `ios.buildNumber` and `android.versionCode` in the same run, writing both back to the local `app.json` (`appVersionSource: "local"`). The Android build's own fingerprint got computed and embedded at a point in that sequence where `buildNumber` was still `"4"`; by the time `eas update` ran afterward, the local `app.json` already reflected the post-build `buildNumber: "5"` — a field with zero actual relevance to the Android binary, but enough to shift the Android fingerprint hash anyway, since the tool doesn't scope the config it hashes per-platform the way you'd expect. `eas fingerprint:compare` output confirms this exactly: `"Modified content: Expo app config" — buildNumber: "4" → "5"`.

**Fixed the same way this workspace already documents for an analogous `package.json` drift issue in the sibling Patron app: temporarily revert the drifted field, publish, then restore it immediately.** Set `ios.buildNumber` back to `"4"` locally, re-ran `eas fingerprint:compare` to confirm it now matched the Android build exactly, republished the Android update (now correctly tagged with the matching runtime version), then restored `buildNumber` back to `"5"` right away. The already-published *wrong* Android update (tagged under the mismatched hash) was left in place rather than deleted — it's inert (no real device's embedded runtime version will ever match it), just harmless clutter in the update history.

**Any future `eas update` published in the same session as an `eas build --platform all` run (or any run where `autoIncrement` touched both platforms) needs the same check — don't assume a clean publish for one platform means the other is fine.** The reliable way to confirm, every time, before trusting a multi-platform OTA push: `eas fingerprint:compare --build-id <build-id>` for each platform's most recent relevant build, immediately after publishing — a "matches" result is real confirmation the update will actually reach that build; a `eas update` command completing without error is not, since a runtime-version mismatch is not a command failure, it's a same-outcome-as-success publish that just never gets served to anyone.

### Stock alert thresholds — one shared rule instead of four disagreeing ones (`utils/stockAlerts.ts`, 2026-09-11)

### DatePickerField — the iOS spinner closed itself after the first wheel tick (`components/DatePickerField.tsx`, 2026-09-11)

Reported plainly as "the date selector is weird" (Commandes clients' "Date de livraison"). Root cause, confirmed against `@react-native-community/datetimepicker`'s own docs before changing anything (Android's declarative component maps internally to the same modal dialog the imperative API shows, for any `display` value — so the Android side wasn't actually the "renders inline" bug it looked like at first guess): iOS's `display="spinner"` has no dialog chrome of its own and fires `onChange` continuously as each wheel (day/month/year, all visible and independently scrollable at once) moves — but the old code called `setShow(false)` straight inside `onChange`, so the picker vanished the instant the user nudged *any single* wheel, often before touching the other two. The date it closed on was whatever partial state existed at that first tick, not what the user meant to pick.

Fixed per-platform: **Android** now uses `display="default"` (the idiomatic system dialog) and only commits on `event.type === 'set'`, closing on either outcome — correct, since Android's dialog fires `onChange` exactly once. **iOS** wraps the spinner in a real `AppModal` sheet with a "Terminé" button; `onChange` now only ever calls the parent's `onChange` (live update as they scroll, matching the library's own reference usage) and never closes the picker itself — only the explicit button does. Both platforms were previously running the exact same close-on-first-tick code with no `Platform.OS` branch at all.

**Follow-up, 2026-09-22: the iOS wheel columns themselves weren't rendering at all — a real, separate sizing bug, not the same one.** Live report: "the calendar is showing up, I don't even see the stuff" — inside the "Terminé" sheet, where the day/month/year wheels should be was a plain empty gray capsule, nothing legible. `<DateTimePicker>` was rendered with no `style` at all — iOS's `display="spinner"` UIDatePicker has no intrinsic size of its own to report, and inside `AppModal`'s `body: { flexShrink: 1 }` wrapper it collapsed to whatever leftover space was implied, rendering as a plain gray track with none of the three wheel columns actually visible. Fixed with an explicit `style={{ height: 216, width: '100%' }}` (216 matches Apple's own standard wheel-picker height). `DateTimePicker` is used in exactly one place in this codebase — this component — so fixing it here covers every screen that renders a date field (Expenses, Production, CustomerOrders, InvestorDetail, PurchaseFormModal) with no per-screen sweep needed; confirmed via `grep -rln "DateTimePicker" .` finding only this file.

### AppModal forms — the submit button could render unreachable behind the keyboard (14 files, 2026-09-12)

Direct bug report with a screenshot: "Nouvel investisseur" (`screens/Investors/index.tsx`) showed Nom/Premier apport with the numeric keypad open, and no way to reach "Ajouter" — only the top hairline of the Annuler/Ajouter buttons peeked out above the keyboard.

**Root cause, not specific to this one screen.** Every form modal in the app follows the same shape: an `<AppModal>` whose `body` is a plain `View` (`flexShrink: 1`, bounded by a `maxCardHeight` that already correctly shrinks to leave room for the keyboard — see the "Design system" RULE above), containing a `<ScrollView keyboardShouldPersistTaps="handled">` of fields followed by a sibling `<View>` of action buttons. The bug: neither the ScrollView nor the button row had `flexShrink` set, and **React Native's Yoga layout defaults `flexShrink` to `0`** (unlike web CSS flexbox, where it defaults to `1`) — so when the keyboard shrinks the available height, nothing in that column is willing to shrink, and Yoga just lets the total content overflow past the bounded body's edge with the default `overflow: visible`, landing underneath the keyboard where it can't be tapped. This is why a numeric keypad (this exact case) doesn't even need much content to trigger it — the bug isn't about "too many fields," it's that **nothing in the layout was ever allowed to shrink at all**, regardless of how little the overflow was.

**First fix attempt (`style={{ flexShrink: 1 }}` on the ScrollView) did not work — confirmed by direct user report after it shipped: "still when adding an investor i don't see no way to click or add to confirm it."** The flexShrink reasoning above was plausible but evidently insufficient on its own — AppModal's own outer sizing/measurement logic (it computes real keyboard height and shrinks/lifts the sheet itself) interacts with the inner ScrollView in a way that didn't reliably leave the sibling button row on-screen, and the exact remaining cause was never fully isolated since a more robust fix was available and taken instead of chasing a second flex-arithmetic variant. Per this file's own standing lesson (see the floating-tab-bar saga in `Patron/CLAUDE.md` for the canonical shape of this mistake): when a class of fix fails, don't try a second variant of the same technique — switch to a fundamentally more reliable primitive.

**Actual fix: move the button row to be the last child *inside* the ScrollView, instead of a sibling after it.** This has no dependency on flex-shrink arithmetic at all — whatever the keyboard-adjusted scroll height ends up being, the buttons are simply part of the scrollable content, so scrolling to the bottom always reveals them, guaranteed. Applied by deleting the `</ScrollView>` that used to sit right before each `<View style={styles.modalActions}>` button row and moving that closing tag to after it instead — across all 14 previously-identified files: `Bulks`, `Clients`, `CustomerOrders`, `Flavors`, `Investors` (list + detail, 3 forms), `Stock` (2 forms), `Suppliers` (list, detail, `PurchaseFormModal`), `Ventes/index.tsx` (price-edit modal), `Ventes/History.tsx` (edit-sale modal — button moved inside the `editForm && (...)` conditional, before its own `</ScrollView>`), `FactorySettings` (weekly-target modal), and `Production` (recipe-editor view and material-creation form — the latter's "Créer" button had no surrounding `modalActions` wrapper, just moved inside the same way).

**Lesson for any new AppModal content going forward: put the submit/cancel button row as the last element inside the fields ScrollView, never as a sibling after it.** A sibling button row outside the scrollable area depends on the surrounding layout correctly reserving space for it under every keyboard/content-length combination — which this codebase already tried and found unreliable in practice. Putting it inside the ScrollView removes that dependency entirely: it's just reachable by scrolling, unconditionally.

### Roles — manager replaces employee, investor scoped down, modernized joining (`db/update27.sql`, `context/AuthContext.tsx`, `lib/inviteLink.ts`, 2026-09-12)

Direct product request to rethink the whole role model from first principles: "manager sees everything, investor sees only his investment, seller just sells — figure out permissions, role changes, and how people join with the simplest modern approach." Researched the actual current RLS/UI state before changing anything (see the three confirmed design decisions below) rather than guessing at what "manager" or "investor-scoped" should mean.

**1. `employee` renamed to `manager`, and widened to true admin-parity except team/factory ownership.** Before this, `employee` could operate day-to-day (log sales/production, manage stock/clients/expenses/suppliers/purchases/customer orders) but could NOT: delete any record, edit the product catalog or prices, or write to investor capital records (`investors`/`investment_entries`/`investor_distributions` were admin-only INSERT/UPDATE/DELETE) — narrower than "sees/can do everything" actually implies. `manager` now has every one of those powers too. The one boundary that stays admin-only, deliberately: approving joins, changing anyone's role, removing members, and factory settings/deletion — so a team's real owner can never be outvoted, demoted, or have the factory pulled out from under them by someone they promoted. Multiple managers (and multiple admins) can coexist freely — `factory_members` has no cap on how many rows share a role, and never did.

**Auditing the Plus screen's menu against the actual RLS grants (not just renaming) surfaced real pre-existing gaps**, not just cosmetic ones: `employee` already had RLS write access to `suppliers`/`purchases`, `expenses`, and `business_documents`, but the Plus menu never showed those screens to that role at all (`roles: ['admin']` only) — and oddest of all, `employee` had no way to reach Bilan/Reports whatsoever despite reading every other operational screen. The menu was simply stricter than the database ever was. Fixed alongside the rename in `screens/Plus/index.tsx` — manager now sees every route admin does except Paramètres.

**2. Investor scoped down to genuinely their own data — a real RLS change, not just hiding UI.** Before this, every "members read X" policy in the schema either had no role filter at all, or (for `investors`/`investment_entries` specifically) excluded only `inspecteur` — meaning an investor could already read every OTHER investor's capital/share amounts too via a raw query, not just their own, even though the Investors screen politely only ever displayed their own row client-side. `db/update27.sql` excludes `investor` entirely from every operational/transactional table's SELECT policy (`sales`, `clients`, `expenses`, `purchases`, `suppliers`, `customer_orders`, `production_batches`/`production_batches_v2`/`production_products`, `stock_items`, `machines`/`machine_status_log`, `business_documents` + its storage buckets, `sale_edits`), and rewrites `investors`/`investment_entries` to properly check `user_id = auth.uid()` (via a join through `investors.user_id` for entries) instead of "anyone but inspecteur." `investor_distributions` was already correctly scoped this way and only needed the role rename. Product catalog (`product_flavors`/`bulk_products`) and the team roster (`factory_members`) are deliberately left universally readable — names/prices and names/roles are low-sensitivity, not the kind of detail this change is about. **Not touched, flagged rather than fixed blind**: `investment_entry_edits`'s read policy is still factory-wide, not scoped per-investor — a real but low-severity residual gap (the UI never surfaces another investor's edit history; `InvestorDetail` only ever opens the viewer's own `investorId`), left alone rather than rewriting a policy with no live database to verify the join against first.

**Two other reachable paths would have silently defeated the RLS restriction if left alone, so both were closed in the same pass**: Orny AI (Coach) is no longer offered to investor in the Plus menu at all — its `getBusinessSnapshot()` reads every operational table directly and would otherwise be a live backdoor to exactly the data just locked down. And Reports (`screens/Reports/index.tsx`) branches on `membership.role === 'investor'` to call the new `get_investor_headline_report(factory_id)` RPC instead of the normal raw-table fetch — a SECURITY DEFINER function replicating `utils/finance.ts`'s `computePeriodProfit()`/`computeCashOnHand()` formulas in SQL (this-month/last-month revenue and profit, cogs-vs-approx method, lifetime cash-on-hand), so the investor's screen can still show real headline numbers without needing direct table access to compute them. The investor's Reports view renders only the profit hero (+ trend vs last month) and Trésorerie — no payment-method breakdown, no credit-outstanding/supplier-debt row, since those are the operational detail this change is specifically about withholding. The RPC itself has no role gate beyond factory membership — the aggregate numbers aren't sensitive in a way that needs restricting further, and admin/manager already see the unaggregated version anyway.

**3. Joining stays approval-based (an admin still assigns the role), but sharing is modernized.** Considered and rejected: instant-join links that add someone immediately with a pre-set role — faster, but a leaked link grants real access until someone notices and removes them, and this app has no existing precedent for that risk trade-off. Kept the existing safety net (a join request lands in `join_requests`, admin picks the role in `FactorySettings`) and fixed the actual friction instead: the invite code used to auto-rotate every 60 seconds (`CODE_TTL`) — realistically too short for a human to copy it, paste it into WhatsApp, and have the recipient open it before it went stale. Raised to 15 minutes; the per-IP rate limit on `lookup-factory` (`db/update7.sql`'s `invite_lookup_log`) is the actual brute-force defense, not this rotation. A new "Partager le lien" button (`Share.share()`, React Native's own core API — zero new native dependency) sends a real link instead of asking someone to manually copy-paste an 8-character code: `lib/inviteLink.ts`'s `buildInviteLink()` constructs `<site>/join?code=XXXX`, using `window.location.origin` on web (always correct) or a hardcoded `PRODUCTION_WEB_URL` constant on native (⚠️ not verified against the real Netlify URL — nothing in this codebase declares it anywhere else, confirm before relying on a native-app share). This works as a genuine universal link with zero extra infrastructure specifically because Orny's own PWA is already the live, functioning app at that URL — there's no separate marketing/landing site needed the way a from-scratch deep-linking setup would require.

**The recipient side needed its own plumbing since `NavigationContainer` has no `linking` config, and FactorySetupScreen isn't reachable through one anyway** — it's rendered directly by `AuthGate` when `!membership`, outside the `Stack.Navigator` entirely, so React Navigation's usual URL-to-screen mapping doesn't apply to it. Instead, `AuthContext` reads the incoming URL directly (`lib/inviteLink.ts`'s `getInitialInviteCode()` — `window.location.search` on web, `Linking.getInitialURL()` + a `Linking.addEventListener('url', ...)` subscription for a warm native app on native) and exposes `pendingInviteCode` through context; `FactorySetupScreen` pre-fills the code and switches to its Join tab on mount, then calls `consumePendingInviteCode()` so it doesn't re-trigger on a later visit. Deliberately does **not** auto-submit the join request — an accidentally reopened link (a forwarded message tapped out of curiosity) shouldn't silently fire off a real request without the person choosing to.

### Cache-first data loading, app-wide (2026-09-05)

Direct request ("fix the way the app is fetching data... when opened up cold... maximise speed and accuracy everywhere"). `context/AuthContext.tsx`'s own cold-start bootstrap was already the correct reference implementation of this pattern — read the local AsyncStorage cache instantly, render, then refresh from Supabase in the background and re-render only if something actually changed — and had needed no changes. Auditing every other screen's `load()` against that same shape found three distinct variants of the same underlying problem, all now fixed the same way (**Ventes**, **Production**, **Ventes/History**, **Investors** already correct, **Reports**, **Stock**, **Expenses**, **Suppliers**, **Flavors**, **Bulks**, **CustomerOrders**, **Documents**):

1. **Blocking sync-then-read** (Ventes, Ventes/History, Clients, Suppliers-partially, Flavors, Bulks) — `await Promise.all([syncXFromSupabase(), ...])` ran *before* the first cache read, so the screen showed nothing (or a stale empty state) until a full network round trip completed, even when a perfectly good local cache already existed. This defeats the entire point of having an offline-first cache — a slow or flaky connection made every screen feel like it has no cache at all.
2. **Fire-and-forget sync that never re-renders** (Expenses, CustomerOrders) — the sync call was correctly *not* awaited before rendering (fast!), but its result was also never read back into state once it resolved, so the screen never actually updated with fresh data after that first paint — a silent staleness bug, not a speed one.

Fix, applied identically everywhere: read cache → `setState` (first paint, instant, no network wait) → `await` every relevant `syncXFromSupabase()` → re-read cache → `setState` again (second paint, only once fresh data actually lands). No store or RPC changed — this is purely a client-side read/render-order fix. `screens/Machines/index.tsx` already independently implemented this exact shape (`getMachines().then(setMachines)` immediately, then `syncMachinesFromSupabase().then(() => getMachines().then(setMachines))`) and was left untouched as a second confirmed-correct reference alongside AuthContext. `screens/FactorySettings/index.tsx` was deliberately **not** touched — its `load()` blocks behind a spinner on purpose: invite codes rotate on a TTL and member/role data is admin-only live state, not offline-cached business data, so showing a stale invite code would be actively wrong, not just slow.

Root cause: `expo-font` was already an existing *transitive* dependency at `14.0.11` (pulled in by something else in the tree) before this pass touched anything — `npx expo install expo-font` bumped the resolved version to `14.0.12` as a side effect, and neither reverting `package.json`'s text nor `npm uninstall`ing the explicit entries rolled that transitive resolution back down; `package-lock.json` and `node_modules` were left one patch version ahead of what the installed binary actually has, and a real (if small) native-module version delta is exactly the kind of thing `@expo/fingerprint` is designed to detect. Confirmed and fixed by explicitly reinstalling the exact prior version (`npm install expo-font@14.0.11 --no-save`) and re-verifying the fingerprint matched every prior publish before ever running `eas update` — caught *before* anything shipped to the wrong place, but only because the fingerprint was cross-checked against the actual publish history (`eas update:list --branch production`) rather than trusted on the first "looks reverted" read. **Lesson: reverting `package.json`'s visible text is not sufficient to undo an `expo install`/`npm install` side effect — a transitive dependency can drift even when nothing in the top-level manifest appears to reference it, and the only reliable check is comparing the freshly-computed fingerprint against a known-good prior publish's actual runtime version, not against expectation.**

### Referential integrity & reconciliation hardening (`db/update24.sql`, 2026-09-06)

Found via a direct security/data-integrity audit (asked "what's the 20% that gets 80% of the value" across reconciliation formulas, security, and product ids) — read every RLS policy in `master.sql`, the full reconciliation function, and traced how each transactional table's "product" column is actually populated client-side before writing anything, rather than guessing from the schema alone.

**The core finding: `sales.product`, `purchases.stock_item_id`, `customer_orders.product`, and `production_batches_v2.product_id` all have zero foreign-key constraint to `product_flavors`/`bulk_products`/`stock_items`** — the exact same "nothing enforces this points at something real" shape that caused the Production/Ventes catalog disconnect (see "Production — produces directly into Saveurs/Lots" above). A real FK is the eventual fix but is bigger/riskier (existing orphaned rows would need cleanup first, and `production_batches_v2.product_id` has *known, disclosed* orphans from the Production/Ventes migration itself — see below); `update24.sql` adds the cheap first step instead: reconciliation checks that would surface it happening again, for the two tables where it's actually a bug class waiting to recur (`sale_orphaned_product`, `purchase_orphaned_stock_item`).

**Deliberately not checked, and why (both traced through the actual screen code, not assumed):**
- `customer_orders.product` — genuinely free text (`screens/CustomerOrders/index.tsx` is a plain `TextInput`, never a picker over real products). A customer can order something not yet in the catalog; flagging this would be a false-positive machine, not a bug detector.
- `production_batches_v2.product_id` — batches logged *before* the Production/Ventes unification fix point at the now-orphaned `production_products` catalog **by design**, already disclosed as an accepted, unfixable-without-data-loss transition cost in that section above. Reconciling against it would just re-flag the same known thing forever, not signal anything new.

**`sale_amount_paid_mismatch` (new check) needed one real trace through the actual payment flows before it could be written correctly — the first draft of this check would have been wrong.** The instinct was "credit sales should always have `amount_paid = 0`," which is false: `screens/Clients/index.tsx`'s "Paiement partiel" and `screens/Ventes/History.tsx`'s "mark paid" both legitimately move a credit sale's `amount_paid` anywhere from 0 up to `total_amount` *without* ever changing `payment_method` away from `'credit'`. The real, checkable invariant is narrower but still fully correct: `store/sales.ts`'s `addSale` always sets `amountPaid = paymentMethod !== 'credit' ? totalAmount : 0`, and **no screen anywhere ever offers a partial-payment path for a non-credit (cash/orange_money) sale** — so a non-credit sale whose `amount_paid` differs from its own `total_amount` is a state the app itself can never produce, making it a clean signal for either a bug or a sale edited after the fact to understate what was actually collected (the same fraud shape Patron's own sibling app has a dedicated check for on its own sale-edit feature).

**Security fix, same migration: `investor_distributions`'s insert/update RLS only ever checked that the caller was an admin of the row's stated `factory_id` — never that `investor_id` itself belongs to that same factory.** An admin of Factory A could in principle write a distribution with `factory_id = A` but `investor_id` pointing at a real investor in Factory B, since nothing cross-checked the two (a plain FK to `investors(id)` only guarantees the investor row exists *somewhere*, not that it's the caller's own). Not reachable through the app's actual UI today (Investors' screen only ever lists/selects investors already scoped to the current factory) — fixed at the RLS layer anyway, the same "the client isn't the only possible caller" posture every other policy in this schema already takes. The update policy gained an explicit `WITH CHECK` for the same reason — without one, Postgres reuses the `USING` clause for both read-eligibility *and* the post-update row, which never re-validated `investor_id` on an edit either.

### Every "add" screen in the app could silently lose the record it just created (17 `store/*.ts` files, 2026-09-16)

Direct report: "I add an investor's name and amount, tap Ajouter, and nothing happens." Reproduced live with a scripted Playwright session against a fresh throwaway factory on the real linked Supabase project (`mtjyeexwvwrhwjzmttmc`) — the tap *did* fire `handleSave`, the modal *did* close, and a direct `supabase db query --linked` confirmed the row landed in Postgres every time. The bug was never in the button. The list just never showed the row, and never would, no matter how long you waited.

**Root cause: every `add*`/`update*`/`delete*` function in every store fired its Supabase write with `.then(({ error }) => ...)` and returned before that promise settled — fire-and-forget, not awaited.** The write-through cache pattern documented at the top of this file ("write to AsyncStorage first, then sync to Supabase in `.then()`") is correct for the *cache* half; the bug is that every screen's own save handler follows the identical shape `await addX(...); await load();`, and `load()` immediately calls `syncXFromSupabase()` — a `SELECT` that unconditionally **overwrites** the local cache with whatever Postgres currently has. Since the insert's own network round trip was still in flight (never awaited), the very next line's re-sync could — and, reproduced live, reliably did — land its `SELECT` response before the `INSERT` committed, so `syncXFromSupabase()` clobbered the correct optimistic cache with a server list still missing the brand-new row. The insert always eventually succeeded server-side; the UI just never found out, because nothing was left to tell it to re-check.

**Why this wasn't caught by tsc, the (nonexistent) test suite, or code review: every individual line looks correct in isolation.** `addInvestor` really does write to AsyncStorage first, really does fire the insert, really does return the new object — exactly what the documented pattern describes. The bug only exists in the *interaction* between one store function returning early and its caller's next line assuming the write is durable. Static review of `store/investors.ts` alone gives no reason to suspect anything; it only surfaces by actually adding something and watching whether it stays on screen a few seconds later, which is exactly how this was confirmed (a screenshot taken 3s after the tap still showed "Aucun investisseur" for a row that direct SQL confirmed existed).

**Fix: every one of these functions now `await`s its Supabase write before returning, keeping the exact same `enqueueIfNetworkError` (or, for `machines.ts`/`documents.ts`, `console.warn`) fallback on the awaited error.** This is not a new pattern invented for the fix — every file's own `delete*` function (and, in `investors.ts`/`investmentEntries.ts`/`investorDistributions.ts`, already correctly awaited) was already written this way; only the `add*`/`update*`/`upsert*` functions had the fire-and-forget mistake, evidently a copy-paste-then-diverge across ~17 files rather than a deliberate choice. Fixed uniformly in `store/investors.ts`, `investmentEntries.ts`, `investorDistributions.ts`, `bulks.ts`, `clients.ts`, `customerOrders.ts`, `expenses.ts` (4 call sites), `flavors.ts`, `products.ts`, `purchases.ts`, `sales.ts`, `suppliers.ts`, `stock.ts` (6 call sites), `batches.ts`, `machines.ts` (4 call sites), `documents.ts`. Verified fixed by re-running the exact same live reproduction (investor now appears immediately and is still there 3s later) plus an independent second spot-check on a completely different store (`clients.ts` — added a client via the real UI, confirmed it persists).

**Trade-off, accepted deliberately: the save button now waits for one real network round trip before the modal closes**, instead of closing instantly against a cache write that might still be racing its own sync. This is the correct trade for data that's about to be immediately re-displayed — the old "instant" close was never actually faster in a way the user could trust, it just *looked* faster while quietly being wrong. True offline behavior is unchanged: a genuine network failure still throws, still gets caught, and still enqueues into `lib/syncQueue.ts` exactly as before — nothing about the offline path depends on the write being fire-and-forget.

**Lesson for any future store function in this codebase: an `add*`/`update*`/`delete*` function that any screen calls immediately before its own `load()`/`syncXFromSupabase()` must await its Supabase write, full stop** — a fire-and-forget write anywhere upstream of an unconditional cache-overwrite is a live data-loss bug, not a theoretical one, regardless of how unlikely the race looks on paper. `store/coach.ts`'s one remaining fire-and-forget call (best-effort "touch last_message_at" on send) was deliberately left as-is — it updates a sort timestamp on data that's already durably saved by the time it runs, not the primary record being created, so losing that race just means a conversation sorts slightly out of order, never that a message disappears.

The document row itself (flat card, file-type-colored thumbnail, category badge, conditional expiry warning) was already fairly aligned with this app's established minimal-list conventions and was left alone — the fix is scoped to the one part that was actually disproportionate.

### `enqueueIfNetworkError` never actually implemented its own documented contract — a real (non-network) write failure was completely invisible in production (found + fixed 2026-09-22)

A live report ("add investor, tap Ajouter, nothing happens") persisted even after the fire-and-forget race fix above had already shipped and was confirmed live — a direct `supabase db query --linked` against the real linked project confirmed no new `investors` row had been created anywhere since May, so this was never the display-only race; the insert genuinely wasn't landing. Schema, RLS (`admin write investors` correctly allows `admin`/`manager`, confirmed the account in question actually holds `admin` in its factory), constraints, and triggers on `investors` were all individually checked directly against the linked DB and came back clean — nothing found there explains an insert genuinely failing for this account.

**What *is* definitely broken, and was the real target of this fix regardless of the exact trigger:** `lib/syncQueue.ts`'s `enqueueIfNetworkError` has always had a comment stating its own contract plainly — "a real rejection (bad data, an RLS/permission error)... silently swallowing that would hide an actual bug" — but the actual code for that branch was `console.warn(...); return;`. Fixed by making `enqueueIfNetworkError` re-throw the original error for a genuine (non-network) failure instead of swallowing it — matching what its own comment already said should happen. Safe across all 14 stores: every call site is a plain top-level `await` inside a normal async function, never inside a background retry loop, so a throw only ever propagates to whichever screen action just triggered the write. ### `crypto` is not a thing in Hermes — broke every single "add" action app-wide, not just investors (found + fixed 2026-09-22)

The Alert added in the fix directly above finally surfaced the real error on the next live attempt: `"property crypto doesn't exist"`. `store/context.ts`'s `generateId()` — called as the very first line of literally every store's `add*` function (investors, clients, sales, expenses, products, everything) — was `return crypto.randomUUID();`. The global `crypto` object (and therefore `crypto.randomUUID`/`crypto.getRandomValues`) is part of a real browser's or Node's Web Crypto API; it does not exist in Hermes, React Native's JS engine, on an actual native build. This is the exact same landmine already documented and already fixed once in this workspace, in the sibling Patron app's `CLAUDE.md`: *"Invite code generation uses `Math.random()` — do not use `crypto.getRandomValues()`, it is not available in Hermes."* Orny's own `context/AuthContext.tsx` had the identical unguarded `crypto.getRandomValues(bytes)` in `regenerateInviteCode()`, never hit/reported only because regenerating an invite code is a much rarer action than adding a record.

**Why this worked fine on the web PWA and looked like an investor-specific/RLS bug on native:** a real browser's `crypto.randomUUID()` works perfectly, so every "add" flow was reproducibly fine on Netlify/web the whole time — the PWA testing earlier in this session never had a reason to doubt the write path itself, only the display-race bug that was actually present there. On the TestFlight (Hermes) build, `generateId()` threw synchronously before any network call was ever made, which is exactly why hours of investigation into `investors`' schema/RLS/constraints/triggers/role all came back clean — the request never reached Postgres at all. It only ever surfaced as "add investor doesn't work" first (and "same for client" the moment the identical pattern was tried a second time) purely because that's the order the user happened to test screens in — every other `add*` call in the app shares this exact same `generateId()` call and was equally broken.

**Fixed by making `generateId()` a plain `Math.random()`-based UUID v4 string** — verified the output actually matches `uuid` column format (`/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i`) before shipping, since every one of these ids gets inserted into a real Postgres `uuid`-typed primary key column — a malformed string here would trade one insert failure for a different one. `lib/syncQueue.ts`'s own separate `crypto.randomUUID()` (for the offline queue's local item id) now imports and reuses this same `generateId()` instead of duplicating the fallback. `AuthContext.tsx`'s `regenerateInviteCode()` got the same `Math.random()`-filled-`Uint8Array` fix Patron already uses for its own invite codes. These three were confirmed to be the **complete** list app-wide via `grep -rn "crypto\." --include="*.ts" --include="*.tsx" .` across the whole repo (excluding `node_modules`) — not a guess scoped to "wherever seemed likely." `supabase/functions/` edge functions were left untouched on purpose — they run on Deno, which has full, real Web Crypto support; this gap is Hermes-specific.

**Lesson for this codebase specifically, now demonstrated twice (once in Patron, once here): never reach for `crypto.randomUUID()`/`crypto.getRandomValues()` in any file that ships to a native RN/Hermes build.** It will type-check fine (TypeScript's DOM lib declares the global), pass every test that runs in Node or a browser-based test runner, and work perfectly on a web/PWA target — and then throw synchronously, immediately, with no network call ever attempted, the first time it actually runs inside the real native app. Grep for `crypto\.` before adding any new dependency on browser-only randomness, and default to a `Math.random()`-based generator for anything that isn't a security-sensitive secret (session tokens, password reset codes) — for opaque row ids and invite codes, this codebase has now settled on that as the standard answer twice.

### `AppModal`-stacking freeze — a bug pattern that had already been diagnosed and fixed once, then got copy-pasted right back into two new screens (found + fixed app-wide 2026-09-22)

With the `crypto` crash fixed, a fresh live report on `InvestorDetail.tsx` — "tap once, it kind of responds, then the whole screen totally freezes; even delete doesn't go through" — is word-for-word the same symptom already described and fixed in `screens/Production/index.tsx`'s own comment: *"tap Voir l'historique, then the whole screen stops responding to taps."* Root cause, unchanged from that original diagnosis: `AppModal` keeps its native `<Modal visible>` actually mounted for a ~180ms JS-driven close animation after its own `visible` prop flips false (see `components/ui/AppModal.tsx`'s `useEffect` — `mounted` only becomes `false` once the closing `Animated.timing` call finishes). A handler that closes one `AppModal`/`ConfirmDialog` and opens a *different* one in the same tap — `setMenuVisible(false); openEdit();` is the exact shape — briefly leaves **two real native modal windows mounted at once**, which is a genuine freeze risk on iOS (UIKit: "Attempt to present \<ViewController\> while a presentation is in progress"), not just a visual glitch.

**This had already been found and fixed once, for Production/Coach/the Suppliers list — but `InvestorDetail.tsx` and `SupplierDetail.tsx` both shipped with it anyway, because `InvestorDetail.tsx`'s own header comment says it "mirrors SupplierDetail's shape exactly."** Whoever built `SupplierDetail.tsx` never hit this bug in the original fix pass (fixed elsewhere, never audited everywhere), so its overflow-menu → edit/delete transitions carried the same anti-pattern from day one — and copying that screen as a template for `InvestorDetail.tsx` copied the bug right along with the shape. **Lesson: a bug fix scoped to "the screen that was reported" doesn't survive being used as a copy-paste template for the next screen** — the fix has to live somewhere a new screen inherits it from automatically, not in institutional memory of which screens were already patched.

**Fixed at the source this time, not per-screen.** `components/ui/AppModal.tsx` now exports `switchModal(close, open)` — closes the first modal, waits `MODAL_CLOSE_MS` (220ms, just past the 180ms close animation) via `setTimeout`, then opens the second — re-exported from `components/ui/index.ts` alongside `AppModal` itself, so any future screen reaches for it from the same place it already imports `AppModal`/`ConfirmDialog` from. Audited every screen in the app for the same shape (a handler closing one modal-backed state and opening a different one) via two passes — a single-line grep for the literal `onPress={() => { setX(false/null); ...}}` form, and a broader multi-line context scan across every screen with 2+ `AppModal`/`ConfirmDialog` instances (the files where this can even occur at all) — and fixed every real instance found: **5 sites across 4 files** — `InvestorDetail.tsx` (3: investor overflow menu → edit/delete, movement-row menu → history/edit, movement-row menu → delete-entry/delete-distribution), `SupplierDetail.tsx` (1 pair: the identical investor-menu shape, confirming it really was copy-pasted), `FactorySettings/index.tsx` (1: member menu → remove-confirm), `Machines/index.tsx` (1: edit form → delete-confirm). `Suppliers/index.tsx` and `Expenses/index.tsx` were checked in full despite having 5 modals each — both came back clean, since every one of their modal-opening triggers fires directly from a list row (nothing else open at the time), not from inside an already-open modal, which is the one shape that's actually safe without `switchModal`.

**Any future screen with more than one `AppModal`/`ConfirmDialog` must route every close-one-open-another transition through `switchModal`, never two bare state setters back to back** — this is now enforceable by pattern (grep for `onPress={() => { set\w+\((false|null)\)` followed by a second, different modal setter) if it's worth wiring into a lint rule later; for now it's a documented convention, the same way "never wrap AppModal's children in your own KeyboardAvoidingView" already is a few sections up.

### Orny AI's "Bilan du jour" quick-prompt chip had genuinely unreadable text — measured, not eyeballed (`screens/Coach/index.tsx`, 2026-09-22)

Reported as "there's stuff trying to say something important, you cannot even read it, like slides but you cannot read." The regular quick-prompt chips (`mossSoft` background + `mossDeep` text) are fine — computed contrast against the real token values in `theme/tokens.ts` comes out to ~4.8:1 in light mode and ~6.4:1 in dark mode, both clearing WCAG's 4.5:1 minimum for small text. The "Bilan du jour" chip (`chipBrief`/`chipTextBrief`) is a different, broken pairing: solid `palette.moss` fill with plain white text — measured contrast ~2.5:1 in light mode and ~1.9:1 in dark mode (dark mode is *worse*, since `moss` is deliberately brightened there for legibility against the dark page background, which makes it a worse backdrop for white text specifically), both badly failing WCAG even under the relaxed 3:1 bar for large/bold text, and this is 12px.

**This is a real, provable defect in the color system, not scoped to just this one chip** — `components/ui/Button.tsx`'s primary variant uses the identical `moss` fill + white text pairing, and computes to the same failing contrast (~2.5:1 / ~1.9:1), used for primary CTAs across the entire app. Left unfixed here on purpose: `Button` is used everywhere, at larger sizes/bolder weight where the failure is less acutely unreadable, and changing its colors app-wide is a much bigger, higher-blast-radius change than this one chip warrants without an explicit ask — flagged as a known, measured, not-yet-fixed issue rather than silently left assumed-fine.

Fixed the chip itself by dropping the inverted fill entirely: `chipBrief` now reuses the same `mossSoft`/`mossDeep` pairing already proven safe in both themes, distinguished from a plain chip by a bold, fully-opaque `moss` border (vs. the regular chip's 25%-opacity one) instead of a color inversion — visually distinct without gambling on contrast math working out. `palette.mossDeep` is documented in `theme/tokens.ts` as literally "the readable-text tone" of the moss 3-slot system (`main`/`Deep`-for-readable-text/`Soft`-background) — `chipBrief` was the one place in the file that didn't follow its own palette's own stated convention.

### Cold-start loading spinner replaced with an extended native splash screen (`App.js`, `navigation/index.tsx`, 2026-09-22)

Direct request: "I don't want to see [the spinner], what's the most innovative solution." `App.js` already used `expo-splash-screen` correctly for one thing — keeping the native splash up until the Inter font finished loading, avoiding a system-font flash — but hid it the instant fonts were ready, which is near-instant (bundled asset, no network) and has nothing to do with whether the app actually has anything to show yet. What the user was actually seeing was `AuthGate`'s own `<ActivityIndicator>` (`navigation/index.tsx`), revealed the moment the native splash disappeared, for however long `AuthContext`'s cold-start session/membership resolution took — which is *not* always instant, since `supabase.auth.getSession()` itself can block on a real network round trip if the stored access token needs refreshing (no local-only fast path for that case).

**Fixed by extending the same native splash to cover that window too, instead of swapping it for a JS-rendered loading screen** — the standard, lowest-risk pattern for this exact problem (native splash → real content, no visible intermediate loading UI on the common path), not a new dependency or native module. `App.js` now hides the splash only once fonts are loaded, a layout pass has occurred (unchanged from before), *and* a new `AuthReadySignal` (a tiny component rendered inside `AuthProvider`, since `App` itself sits above the provider and has no context access) reports that `AuthContext`'s one-time cold-start `loading` flag has resolved. On a normal open — valid cached session, cached membership — this whole window is milliseconds, so the native splash now simply stays up through it and the user goes straight from splash to real content with no visible spinner at all, which is what "most innovative solution" actually cashes out to here: not a fancier spinner, no spinner.

**A hard 8-second timeout (`AUTH_READY_TIMEOUT_MS`) force-resolves splash-hiding regardless of auth state** — `AuthContext`'s own cold-start path already bounds its worst case (a 5s race on the no-cached-membership branch), but `getSession()`'s own potential token-refresh network call has no such bound. Without this ceiling, a genuinely stuck/offline cold start would leave the native splash on screen forever, which reads as a hung or crashed app — strictly worse than the spinner it's replacing. This timeout is what keeps the change a pure improvement rather than trading one failure mode for a worse one.

**`AuthGate`'s own fallback spinner (still needed for the rare cases that actually outlast the extended splash: first install with nothing cached yet waiting up to 5s for network, or the 8s safety timeout firing) had its own smaller bug, fixed in the same pass: its background was `palette.paper` (themed, near-white in light mode / near-black in dark), while the native splash it's meant to continue from is a fixed, non-theme-aware `#10B981` (`app.json`'s `expo.splash.backgroundColor`, native config, not adaptable to light/dark without a fresh build).** In the rare case this fallback actually shows, the two colors would visibly clash — the exact "jarring flash" this whole change exists to remove, just relocated to the one case still reachable. Split into two branches: `loading`/`membershipLoading` (provably cold-start-only — `setLoading` is only ever called from `AuthContext.tsx`'s `boot()`) now renders a new `coldStartSplash` style hardcoded to the same fixed `#10B981` with a white spinner — a deliberate, commented exception to "always use palette tokens," since it exists specifically to match a native value that itself isn't themed. `isTransitioning` (a separate, later-in-session case — a factory switch, well after the real themed UI has already rendered) keeps the original themed `palette.paper` background, since re-flashing to splash green mid-session would itself be the wrong call there.
